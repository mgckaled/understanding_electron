# 18-F — Anexo de Excel (`.xlsx`)

**Depende de:** [18-A — Motor: instalação, endurecimento e a primeira travessia de processo](../implemented/18-A-motor-e-worker.md) (implementado) · [18-B — Canal, Arrow e a primeira consulta visível](../implemented/18-B-canal-e-consulta.md) (implementado) · [18-C — Pré-visualização automática](../implemented/18-C-pre-visualizacao.md) (implementado) · [18-D — Perfil nível 2 e o cartão aninhado](../implemented/18-D-perfil-e-cartao-aninhado.md) (implementado) · [18-E — Anexo de JSON e NDJSON](../implemented/18-E-json-ndjson.md) (implementado) · **Entrega:** anexar um `.xlsx` de uma única planilha (primeira linha como cabeçalho, valores calculados) pelo mesmo caminho que hoje aceita CSV/TSV/TXT/JSON/NDJSON — mesmo `DatasetCard`, mesma pré-visualização, mesma consulta, mesmo perfil, sem tocar nenhum dos quatro.

> Sexto e último sub-plano do arco 18. Ao contrário do 18-E ("generaliza quase de graça"), este **não generaliza de graça** — e não por acaso: `docs/plan/implemented/18-A-motor-e-worker.md` já nomeou isto no próprio Risco 4, escrito há seis sub-planos, antes de qualquer um deles existir: *"a lista de extensões fica vazia até o 18-F [...] se o 18-F descobrir que `LOAD` também precisa de alguma configuração que só pode ser setada depois do lock, a sequência da D18A.3 precisa reabrir — mas é um risco conhecido e nomeado, não uma surpresa."* Este plano é a primeira vez que `extensionPaths` (`core/duckdb/config.ts`, vazio desde o 18-A) recebe uma entrada de verdade. Tratado com o mesmo cuidado que o 18-A deu ao entrypoint do worker: resolver a maior incerteza **primeiro**, ao vivo, antes de construir qualquer coisa em cima dela.

**Fora deste plano:** `.xls` binário legado (contêiner OLE2, não ZIP — um parser completamente diferente, sem o `excel` extension do DuckDB) · seleção de planilha (workbook com mais de uma aba: lê-se a que o motor escolher por padrão, comportamento só observado, não escolhido pela UI) · células mescladas · fórmula como expressão (só o valor já calculado) · escrita/exportação (`COPY ... TO FORMAT xlsx` — nenhum sub-plano do arco 18 tratou escrita ainda; fica para quando existir o pipeline de tratamento, `ROADMAP.md`'s "depois do arco") · datas seriais cruas quando a célula de origem não está formatada como data no arquivo (herdado do dado de entrada, mesmo princípio que já vale para "decimal com vírgula" em CSV, `ESCOPO.md`) · suporte a plataforma além de win32-x64 para o binário da extensão vendorizado (a mesma fronteira que `asarUnpack`'s `@duckdb/node-bindings-win32-x64` já assume desde o 18-A).

## O que a leitura dos planos implementados mudou neste desenho

Sete fatos do código real — `core/duckdb/{config,query,schema,protocol}.ts`, `core/dataset/{format,hashedLines}.ts`, `workers/duckdb/index.ts`, `main/duckdb/spawnWorker.ts`, `main/features/dataset/{handlers,attachJson,lines}.ts`, `main/ipc/register-all.ts`, `electron-builder.yml`, `renderer/.../AttachButton.tsx` — lidos antes de qualquer decisão abaixo, mais duas confirmações no Context7 (`duckdb-web`):

1. **`buildDuckDbStartupCommands` (`core/duckdb/config.ts`) já implementa a ordem load-antes-de-travar da D18A.3 — e já carrega o `LOAD` de cada `extensionPaths[i]` como a primeiríssima linha, antes de qualquer `SET`.** A função está pronta para receber uma entrada; ninguém nunca passou uma. O trabalho deste plano é popular `extensionPaths` com um caminho real, não redesenhar a sequência.
2. **A ordem real, corrigida ao vivo na execução do 18-A, difere do pseudocódigo original do 18-A**: `allowed_directories`/`temp_directory` têm que ser setados **antes** de `enable_external_access = false`, não depois — o comentário em `config.ts` documenta os dois erros exatos que o DuckDB devolve se a ordem for trocada. Achado por engano em 2026; para este plano, só importa que a ordem hoje é `LOAD` → `allowed_directories`/`temp_directory` → `enable_external_access = false` → `autoinstall/autoload_known_extensions = false` → `memory_limit` → `lock_configuration = true`, e que ela nunca foi exercitada com uma extensão real carregando.
3. **`resources/**` já existe como convenção de recurso binário vendorizado, versionado no git, extraído do `asar`** — `electron-builder.yml` já lista `resources/**` em `files` e em `asarUnpack`, hoje servindo só `icon.png`/`logo-proposta-monograma-c.svg`. Este plano é o segundo consumidor desse mecanismo, não o primeiro a inventá-lo — mas o primeiro a precisar que um processo **worker** (não o main, não o renderer) resolva o caminho, o que nenhum dos dois arquivos existentes fez até hoje (`icon.png` é lido só pelo main, via `?asset` do electron-vite).
4. **`sniffDatasetFormat` (`core/dataset/format.ts`, 18-E) opera sobre `string`, decodificada via `.toString('utf8')` nos dois pontos de chamada (`main/features/dataset/lines.ts`, `workers/duckdb/index.ts`)** — correto para CSV/JSON, que são texto; `.xlsx` é um contêiner ZIP binário, cujos primeiros 4 bytes (`50 4B 03 04`, `"PK\x03\x04"`) precisam ser reconhecidos **antes** de qualquer decodificação de texto, não depois.
5. **`hashedLines` (`core/dataset/hashedLines.ts`) decodifica cada chunk via `StringDecoder('utf8')` para produzir linhas — e é isso que `attachJsonDataset` reaproveita só para drenar o hash, sem usar as linhas** (comentário no próprio arquivo: "`lines` é drenada só para alimentar `digest()` — nenhum parsing acontece aqui"). Rodar `StringDecoder` sobre um `.xlsx` inteiro decodificaria bytes binários como texto UTF-8 inválido (substituindo por U+FFFD em silêncio) e acumularia esse texto descartável inteiro em memória até achar um `\n` — desperdício real, agravado pelo próprio teto de memória que `ESCOPO.md` já registra para Excel (5–10× o tamanho do arquivo).
6. **`attachJsonDataset` (18-E) já resolve a ordem hash → guarda → `runSchema`, forçada por `allowed_directories` (D18A.3): o worker nunca enxerga o arquivo original do usuário, só a cópia em `attachmentsDir`.** Essa restrição não é específica de JSON — vale para qualquer formato, então o caminho de Excel repete a mesma ordem, não uma nova.
7. **Confirmado no Context7 (`duckdb-web`):** o `excel` extension é uma extensão **core** do DuckDB (não *community*), e desde a 1.2 lê (`read_xlsx`) e escreve (`COPY ... FORMAT xlsx`) de verdade — antes disso, servia só para computar fórmulas. `read_xlsx` aceita `header`, `sheet`, `all_varchar`, `ignore_errors`, `range`, `stop_at_empty`, `empty_as_varchar`; tipo por célula é inferido da **formatação** da célula (`DATE`/`TIME`/`TIMESTAMP`/`BOOLEAN` quando o Excel de origem formatou assim, não um número serial cru lido como `DOUBLE`). A doc consultada não afirma qual planilha `read_xlsx` lê quando `sheet` não é passado e o *workbook* tem mais de uma — só observável ao vivo (Risco 3).

## Decisões

### D18F.1 — Vendorizar o binário da extensão; `LOAD` por caminho explícito finalmente exercitado

`INSTALL excel; LOAD excel;` é o caminho padrão do DuckDB — mas baixa da rede, e o motor do app roda com `enable_external_access = false` em definitivo (não uma trava que liga e desliga; ver `ESCOPO.md`/seção Segurança do `CLAUDE.md`). A D18A.3 já resolveu isso por pesquisa, seis sub-planos atrás: `LOAD` aceita um caminho de arquivo `.duckdb_extension` local, sem tocar `autoinstall_known_extensions`. O que faltava — e é o primeiro passo deste plano — é **ter** esse arquivo.

**Obtenção é uma ação de desenvolvimento, fora do app, uma vez:** um script descartável (fora de `src/`, não parte do produto) usa o **mesmo** `@duckdb/node-api@1.5.5-r.4` já instalado, contra uma instância `:memory:` **sem** a config restrita, e roda `INSTALL excel; LOAD excel;` normalmente — isso baixa e cacheia o `.duckdb_extension` no diretório padrão do DuckDB para esta máquina. O arquivo é então copiado para `resources/duckdb-extensions/excel.duckdb_extension` e commitado — mesmo tratamento que `resources/icon.png` já recebe hoje (binário versionado no git, sem LFS, sem precedente de tamanho problemático no projeto). **Casamento de versão importa**: o binário da extensão é vinculado ao build exato do DuckDB que o gerou — usar a mesma versão de `@duckdb/node-api` que já está fixada em `package.json` para obtê-lo é o que garante compatibilidade, não uma suposição a parte.

**Achado do advisor, aplicado antes de escrever o passo 1**: a doc do Context7 também mostra `LOAD` de caminho local exigindo `allow_unsigned_extensions` para um binário **não assinado**. A leitura mais provável é que o `excel` core extension, obtido do canal oficial, chega assinado — mas isso não está confirmado, só suposto. Se estiver errado, a correção **não é um `SET`**: `allow_unsigned_extensions` é opção de **criação de instância** (`DuckDBInstance.create(':memory:', { allow_unsigned_extensions: true })` ou equivalente), fora da sequência que `buildDuckDbStartupCommands` monta — mudaria `workers/duckdb/index.ts`'s chamada a `DuckDBInstance.create`, não `core/duckdb/config.ts`. É o Risco 4 do 18-A se materializando num lugar diferente do que o pseudocódigo original imaginou (a fronteira de criação da instância, não a ordem dos `SET`) — nomeado aqui para não ser uma surpresa se acontecer. O passo 1 existe para descobrir qual dos dois branches é real, não para presumir o mais provável.

Escopo de plataforma: só win32-x64, a mesma fronteira que `@duckdb/node-bindings-win32-x64` já assume em `asarUnpack` desde o 18-A. Vendorizar para outras plataformas é gatilho de `ROADMAP § 2`, não deste plano.

### D18F.2 — Caminho do recurso resolvido no *main*, nunca no bundle do worker

`icon.png` é resolvido via `?asset` do electron-vite — mecanismo de resolução de import em tempo de build, testado até hoje só na entrada `main` do bloco principal (D18A.1 já registrou como **não confirmado** se esse bloco se comporta igual na segunda entrada, a do worker — a pergunta ficou em aberto porque nada até agora precisou de um asset ali). Este plano evita empilhar essa incerteza: o caminho do binário da extensão é resolvido **só no processo main**, onde `?asset`/`process.resourcesPath` já são terreno conhecido (mesmo padrão de `icon.png`), e passado ao worker como um argumento de `fork()` a mais — exatamente como `userDataPath` já viaja hoje (D18A.2: o worker nunca importa `electron`, só recebe string por `process.argv`).

```ts
// main/duckdb/spawnWorker.ts
export function spawnDuckdbWorker(userDataPath: string, extensionPath: string): UtilityProcess {
  const worker = utilityProcess.fork(join(__dirname, 'duckdbWorker.js'), [userDataPath, extensionPath], { stdio: 'pipe' })
  // ...
}
```

`registerAll.ts` resolve `extensionPath` uma vez (`app.isPackaged` decide entre `app.getAppPath()`-relativo em dev e `join(process.resourcesPath, 'app.asar.unpacked', 'resources', 'duckdb-extensions', 'excel.duckdb_extension')` empacotado — o layout que `asarUnpack: resources/**` já produz, sem inventar convenção nova) e passa para `spawnDuckdbWorker`. `workers/duckdb/index.ts` lê `process.argv[3]`, monta `extensionPaths: [extensionPath]` no lugar do array vazio que `main()` passa hoje para `buildDuckDbStartupCommands`.

### D18F.3 — Terceiro formato decidido por bytes mágicos, não por texto

`DatasetFormat` ganha `'excel'`. `sniffDatasetFormat` muda de assinatura — `(sample: string)` vira `(sample: Buffer)` — porque um contêiner ZIP não é texto e não deve ser decodificado como tal só para ser reconhecido: os 4 primeiros bytes de um `.xlsx` são a assinatura ZIP `50 4B 03 04` ("PK\x03\x04"). A função checa essa assinatura **primeiro**, sobre os bytes crus; só se não bater, decodifica UTF-8 e aplica a lógica já existente (BOM, `{`/`[` → `json`, resto → `delimited`).

Os dois pontos de chamada (`main/features/dataset/lines.ts`'s `sniffFileFormat`, `workers/duckdb/index.ts`'s `sniffFileFormat`) passam a entregar `buffer.subarray(0, bytesRead)` direto, sem `.toString('utf8')` antes. A garantia da D18E.1 — main e worker nunca podem discordar, porque rodam a mesma função sobre os mesmos bytes content-addressed — continua valendo sem mudança de princípio, só de tipo de entrada.

### D18F.4 — Hash de arquivo binário não passa por `StringDecoder`

`hashedLines` existe para decodificar texto em linhas **enquanto** alimenta o hash — adequado para CSV (onde as linhas são o produto) e reaproveitado por JSON só pelo efeito colateral do hash (D18E.3, achado 5 acima). Para Excel não existe produto nenhum em "linhas": ler um `.xlsx` byte a byte como texto UTF-8 decodificaria um binário, seria descartado de qualquer forma, e ainda acumularia a string decodificada inteira em memória até esbarrar num `\n` — desperdício real, não só estético, no formato que `ESCOPO.md` já nomeia como o mais caro em memória (5–10×).

Novo helper, ao lado de `hashedLines` em `core/dataset/hashedLines.ts`: `hashFile(chunks: AsyncIterable<Buffer>, hash: ReturnType<typeof createHash>): Promise<void>` — um `for await` que só chama `hash.update(chunk)`, sem `StringDecoder`, sem buffer de string, sem `yield`. `main/features/dataset/lines.ts` ganha `hashOnlyFile(path)` no mesmo formato de `readHashedFile` (stream + hash), mas usando `hashFile` em vez de `hashedLines`.

`attachExcelDataset` (novo módulo, ao lado de `attachDelimitedDataset`/`attachJsonDataset`) usa `hashOnlyFile` → `storeAttachment` → `runSchema(hash)` — a mesma ordem hash-guarda-schema do JSON (achado 6 acima), porque a mesma restrição de `allowed_directories` se aplica: o motor só enxerga `attachmentsDir`, nunca o caminho original.

### D18F.5 — `read_xlsx` via o mesmo `ensureDatasetView`; `runSchema`/`hasNestedType` sem mudança

`buildViewSqlInterpolated` ganha um terceiro ramo: `format === 'excel'` monta `CREATE OR REPLACE VIEW dataset AS SELECT * FROM read_xlsx('<path>', header = true)`. Sem cláusula de encoding — `.xlsx` não tem ambiguidade de charset (células são tipadas, não bytes crus a decodificar), mesmo raciocínio que já livrou JSON da dança de `latin-1` (D18E.5, "pula a dança de encoding inteira").

`kind: 'schema'` (protocolo, `runSchema`, fila `createEnqueue`) não ganha um quarto tipo de requisição — o mesmo pedido que já serve JSON serve Excel: `ensureView` já despacha por `format`, `handleSchema` já roda `DESCRIBE`+`hasNestedType`+`COUNT` sobre a *view* `dataset`, não sobre o formato de origem. `hasNestedType` nunca vai disparar para uma planilha (uma célula não produz `STRUCT`/`MAP`/`LIST` — é a própria natureza tabular do Excel), mas rodar o mesmo caminho sem um `if` condicional é mais simples que abrir uma exceção só para este formato.

### D18F.6 — Interface e os limites explícitos do caminho simples

`pickDataset` ganha `xlsx` no filtro combinado (`main/features/dataset/handlers.ts`, já com `csv/tsv/txt/json/ndjson/jsonl`) e um terceiro `filters` dedicado (`{ name: 'Excel', extensions: ['xlsx'] }`), mesma forma dos dois já existentes. `AttachButton.tsx` ganha um terceiro ramo condicional: `format === 'excel'` renderiza "Formato: Excel" (mesma posição da linha "Formato: JSON", sem planilha/aba mostrada — o caminho simples não expõe seleção). `datasetPartSchema.format` vira `z.enum(['delimited', 'json', 'excel'])`.

`DatasetCard`, `DatasetPreview`, `DatasetQueryPanel`, `DatasetProfile` — mesma aposta do D18E.6, pelo mesmo motivo (nenhum dos quatro sabe que existe mais de um formato, só fala de `hash`/`view dataset`) — **não deveriam mudar uma linha**, mas isso só vale como fato depois de provado ao vivo no passo 5, não antes: um `.xlsx` real pode produzir `TIMESTAMP`/`DATE`/`BOOLEAN` por um caminho (`DuckDBTimestampValue` do `read_xlsx`) que `normalizeColumns.ts` nunca viu exercitado — a mesma classe de achado que o 18-E teve de verdade (`DuckDBTimestampValue` do JSON precisou de correção em `normalizeColumns.ts`, ver diário do 18-E). O passo 5 existe para descobrir se Excel repete isso ou não, não para presumir que já está coberto.

**A mesma armadilha que o 18-E pagou uma vez, nomeada para não pagar de novo**: o diário do 18-E registra o advisor corrigindo o ramo condicional para `format === 'json'` (positivo), nunca `=== 'delimited'` — porque uma parte persistida antes do 18-E volta do banco com `format: undefined` (a leitura de `conversation:messages` nunca valida `parts` com zod), e precisa cair no ramo "Separador" como qualquer CSV antigo. O terceiro ramo deste plano segue a mesma forma: `format === 'excel'` primeiro, `format === 'json'` depois, **`undefined`/qualquer outra coisa cai no `else` (Separador)** por último — nunca um `switch` que trate `undefined` como caso especial à parte.

## Ordem de dependência

```
1 (vendorizar + prova isolada) ──► 2 (caminho main→worker + prova dev/empacotado) ──►
  3 (sniff/hash binários puros) ──► 4 (view/attach/filtro) ──► 5 (UI + prova ao vivo) ──► 6 (fechamento)
```

Linear, com um detalhe que difere do 18-E: os passos 1 e 2 são **verificação antes de construção** — a mesma ordem que o 18-A usou para o entrypoint e a config travada — porque são exatamente onde o Risco 4 do 18-A apontou a incerteza real. Só depois de 1 e 2 confirmarem que a extensão carrega e sobrevive ao empacotamento é que os passos 3–5 (que são, em si, o mesmo tipo de trabalho que o 18-E já fez três vezes) valem a pena escrever.

## Riscos

1. **Tamanho do binário vendorizado não medido antes de executar** — extensões DuckDB variam de centenas de KB a alguns MB; sem precedente de LFS no projeto, um binário de poucos MB no git é aceitável, mas o número real (passo 1) decide se isso continua verdade — registrar, não estimar.
2. **`resources/**`/`asarUnpack` nunca foi exercitado para um arquivo que o *worker* (não o main) precisa resolver em runtime** — mitigado por design (D18F.2: resolvido só no main, passado por argv), mas o resultado final ainda depende do layout que `asarUnpack: resources/**` produz de fato dentro de `app.asar.unpacked`, e isso só se confirma com `pnpm build:win` (passo 2), não por leitura do `electron-builder.yml`.
3. **Planilha padrão sem `sheet` explícito, para um workbook com mais de uma aba, não está documentada** (achado 7, seção anterior) — o passo 5 observa o comportamento real com um fixture de duas planilhas; se não for "a primeira", ou se o motor exigir `sheet` explícito nesse caso, é achado para `ROADMAP § 2`, não bloqueante para fechar este plano (a decisão de produto "qual planilha" já está fora de escopo, D18F acima).
4. **`allowed_directories`/`enable_external_access` nunca foram confirmados contra `read_xlsx` especificamente** — plausível que sigam o mesmo mecanismo de trava por caminho que `read_csv_auto`/`read_json_auto` já respeitam (é o motor, não o leitor de formato, que aplica a trava), mas não testado até este plano; passos 4/5 confirmam ao vivo, mesma régua que o 18-A deu à trava em si (passo 4 do 18-A).
5. **Célula de data não formatada como data no arquivo de origem** — `read_xlsx` provavelmente devolve o serial numérico cru como `DOUBLE`, não erra; é o dado de entrada ambíguo, não um defeito do app (mesma classe que "decimal com vírgula" em CSV, `ESCOPO.md`) — aceito, não uma correção a fazer.
